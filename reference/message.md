# Message and structure

## The five blocks

Start here, and cut rather than add.

1. **Hero:** what it is, who it's for, the primary CTA, and the real product. Within the first
   screen, because that's where most attention goes.
2. **Proof:** a demo, real footage, a real quote, or a sourced number.
3. **What it does:** only what the reader needs in order to act.
4. **Trust or objection:** pricing, privacy, limits, an honest "not for you if".
5. **Final CTA and footer.**

Each extra section must answer an objection named in the brief. Cut by default, but keep anything
that answers a real objection: short pages aren't automatically better. Higher prices and colder
audiences may need more, though that's opinion rather than measured fact.

## Rules

- A stranger can say what it is and who it's for within ten seconds.
- One goal per page, plus at most one lighter secondary action. Repeating the same CTA is fine.
- Write at about a grade 5-7 reading level, except where the audience needs precise terms.
- Say the specific thing. "Replays every Flutter session" beats "Unlock your potential". Prefer
  "Download for Mac" over "Get started".
- No headline formula is proven. Default to plain words naming an outcome for an audience.
- Forms ask for the fewest fields that work. Drop phone and age first.
- A few real, specific proof points beat many vague ones. One real quote is enough early on.
- Show a price, a range, or a worked example. Hiding it loses people.
- Use an FAQ only for real objections. It no longer earns a rich result.
- No auto-rotating carousels. Don't use stock people.

## Developer audiences

Lead with the command or a code sample. Link docs and GitHub near the top. Don't gate anything
behind a sign-up. State security, privacy and pricing plainly, because those are the top reasons
developers reject a tool.

Not every tool has a command. Lead with the first of these that's real:

1. A short code sample, for a library used from code.
2. A real request and its response, for a hosted API.
3. A real screenshot or real output, for a tool used through an app, editor or website.
4. The repository or docs as the primary CTA, when none of those exists yet.

Whatever leads has to work today. Never write an install command for something that isn't
published, or a package name you haven't checked. If nothing can be installed or used yet, the page
is pre-launch.

## Consumer app audiences

Use official store badges unmodified, at least 40px high, App Store first, below the main message.
Apple's credit lines apply. On mobile use a small banner, never a full-page interstitial.

## Proof and honesty

Every number needs a definition, a date and a source in the brief's claims table.

- The project's own README is not a source for a number, date, version, licence, price, security,
  privacy or availability claim. It can back only a plain description, marked `README only`.
- Testimonials must come from real people who used the product. Disclose insiders and any
  incentive. Don't cherry-pick in a way that misleads. Fake reviews, including AI-written ones,
  are illegal under the FTC rule, with penalties up to $53,088 per violation.
- Never claim a rating or review you don't have, including in structured data.
- Never claim accessibility compliance through an overlay.
- Competitor claims must be true on the date shown, and a comparison must say where they win.
- A privacy claim must match the scripts that load.

## Things that make a page read as generated

These are tells, not proof, and one alone isn't a failure. Avoid stacking them.

- **Design:** Inter everywhere, serif-italic accent word, purple gradients, glows, permanent dark
  mode with grey text, a badge above the H1, coloured card edges, identical icon cards, numbered
  1-2-3 steps, stat rows, emoji icons, all-caps labels, glassmorphism.
- **Copy:** "It's not just X, it's Y", reflexive groups of three, inflated significance, "serves
  as", "delve", "pivotal", "seamless", "unlock", "elevate", "game-changing".
